# ADR-0001 — Модульный кор: kernel + модули с контрактами + порты

| | |
|---|---|
| **Статус** | accepted (user + оракул, 2026-07-11) |
| **Контекст** | миграция фреймворка из оракула (capsule); кор-предок — монолит: каждая фича = вскрытие движка, UiProxy размазан по engine и знает наш кит напрямую |

## Решение

Кор weber — **microkernel**: целостный движок, СОБИРАЕМЫЙ из модулей.

1. **Kernel** (`@weber/kernel`) — тонкий: контракт модуля (`defineModule`,
   `IWeberModule`), порты, единый HCA runtime-контекст. Механик в kernel нет.
2. **Модуль кора** (`core/<name>`, пакет `@weber/<name>`) — внутренняя механика
   движка: интегрируется НАПРЯМУЮ (in-process, без адаптеров), наружу отдаёт
   только декларированный вход/выход: вход = конфиг/конвенции (мержатся поверх
   дефолтов), выход = typed API. Module-global state запрещён — инстансы
   независимы (`create()` per engine).
3. **Порт кора = мост пакета** (одна механика): внешние нужды (state, router,
   query, …) модуль объявляет интерфейсом в kernel (`ports.ts`); пакеты
   (`packages/*`) реализуют адаптеры. Импорт реализации пакета внутри
   модуля невозможен by construction — у модуля есть только порт.
   Следствие решения user «web-state не в коре»: FSM-шов оформляется портом
   при переносе logic-механики; `@weber/state` = первый адаптер (пакетная волна).

## Правила нарезки

- **По фактическим швам, по одному, при переносе** — не проектировать контракты
  на бумаге (принцип мостов). Первая нарезка = естественные механики предка:
  ui-proxy · controller-proxy · logic-wrapper · slot-registry · providers/bootstrap.
  Мельче не резать: пере-дробленный кор хуже монолита.
- **Zero-cost контракты**: интерфейсы и типы, не runtime-обёртки вокруг вызовов;
  реактивные примитивы Solid проходят границу first-class (геттеры/функции
  в mergeProps, не снапшоты).
- **Сборка (engine assembly)** — НЕ проектируется заранее: появится со вторым
  модулем и обёртками, вырезанная по реальной потребности.

## Эталон модуля

`@weber/ui-proxy` (первый вырез): kit-agnostic — конвенции (kindTags, events,
passthrough, marker) = вход, `proxy/wrapComponent/bindEvents` = выход, стор —
только через `IStorePort`. Конформанс-сьют = порт капсульного + контракт
параметризации.

## Комьюнити-модули («майнкрафт с кодом») — вижн, не сейчас

Юзер пишет не только пакеты, но и модули движка; подмена модуля в тест-зоне,
выбор модуля потребителем, конкурсы кандидатов. **Судейство = conformance-suite
на контракт** (тот же паттерн, что brainer-kernel: один контракт — N реализаций).
Открываем ПОСЛЕ стабилизации контрактов (наши модули пережили реальные
итерации через свой же публичный контракт — догфуд «юзер умеет всё, что и мы»).
Supply-chain (чужой код в чужом проде): реестр/ревью — проработка фазы
маркетплейса, отдельным ADR.

## Отвергнуто

- Перенос кора as-is (монолит) с последующим рефакторингом — двойная работа,
  теряется момент миграции как форсирующая функция нарезки.
- Полный DI-фреймворк/граф зависимостей модулей на старте — оверинжиниринг
  при одном модуле; сборка вырастет из реальных швов.

## Следствия

- CC-4 (build-time dep в коре) умирает by construction — build-infra не модуль
  рантайма. CC-10 (store.ctx typing) гасится типизацией порта (`IStorePort<TCtx>`).
- Каждый модуль: OWNERSHIP.md + conformance-тесты + честные deps (kernel + peer solid).
